# Drop Engine architecture decisions

Status: proposed for user approval. These decisions are not implemented or approved by silence. Technical constraints are recorded in [wix-api-verification.md](wix-api-verification.md).

## Installation, identity, and data ownership

Use trusted installation `instanceId` and `siteId` on every read and write. A new clone gets its own installation and billing state even if `originInstanceId` links it to another site. Do not copy subscriber PII or active gates into the cloned site's new installation automatically. Detect catalog version per installation and revalidate rather than caching permanently across the process.

Collections and index proposals (all IDs prefixed with `@admin14744/drop-engine-for-stores/`):

## Concurrency and publication

Data has documented conditional updates and duplicate-ID rejection but no verified cross-collection transaction. A version field is useful only with a server-enforced condition. Prefer a canonical single drop document for enforcement, immutable receipts, deterministic outbox jobs, and reconciliation for secondary records.

Activation must not be a naive overlap-query followed by insertion. Verify an installation-level conditional publication lock/reservation so concurrent drop creation cannot activate overlapping product windows or exceed the Free active limit. Publication should move from a prepared draft to a committed active rule only after required association writes/claims succeed; reconcile abandoned preparations. A process-local mutex does not protect multiple Wix instances. Test this before enabling merchant scheduling.

The waitlist cap also needs a persistent claim or verified conditional installation counter/reservation. Count-then-insert and in-memory throttling are not concurrent quota enforcement. Plan the refund/reconciliation path for claimed capacity whose insert fails.

Use primary/consistent reads for gate changes and fresh version fences; batch enrolled product checks. Treat unavailable storage differently from absent rules: return a clear ERROR on a caught inability to establish purchasing eligibility. When affected items cannot be identified, the safest app-side proposal blocks the request broadly and reports an outage. This availability tradeoff needs live testing and merchant-visible diagnostics. Wix platform callback outage semantics remain unresolved; do not advertise unconditional fail-closed protection.

## Time and lifecycle

Store UTC instant, original local timestamp, IANA timezone, and DST disambiguation. Reject nonexistent local times. For repeated local times ask for the earlier/later instant; do not parse datetime-local using the server's local timezone. Reschedule, release, cancel, and restore increment rule version. Jobs use that version as a fence; old jobs cannot mutate state or send notifications.

Effective lifecycle derives from authoritative time and control state. Launch interval is `[launchUTC,endUTC)`; no end means ongoing live purchasing subject to plan safety semantics. Release early replaces launchUTC with current server time, preserving an audit record. Cancellation restores ordinary purchasing immediately. Duplicates become drafts with no subscribers/jobs. Deleted products invalidate configuration with an actionable error rather than mutating unrelated catalog items.

## Consent, analytics, retention, and operations

Signup requires explicit consent language, server schema validation, provider-independent unsubscribe state, private hash deduplication, persistent rate limits and verified bot protection. Do not claim email delivery until provider webhooks confirm it. Cap counters, signup counts, and analytics derive from real persisted records; public count endpoint returns no emails/contact IDs.

Define units sold as net eligible units of enrolled products ordered during the live interval, with current order/payment/refund state reconciled. Define waitlist-to-buyer conversion as unique consented subscribers matched to eligible buyers divided by unique eligible subscribers, with identity match policy disclosed. Overall product sales are a separate figure. Emails sent/delivered are provider state counts; no email-click attribution without evidence. Date filters use explicit UTC intervals and localized display.

Retention duration and automatic deletion after uninstall are still open. Removal must stop enforcement and notifications without relying on unsupported post-uninstall Wix mutations. Collections may remain; disclose this and verify platform retention/access behavior. Do not promise a post-uninstall cleanup timer without a supported identity and approved trigger. CSV exports require server-side entitlement/installation checks, injection-safe cell encoding, no caching, and safe log redaction.

Operational details, `.env.example`, production backup/export procedures and alert integrations become concrete after the relevant services and secret storage contracts are approved. They must describe actual implemented behavior, not hypothetical setup commands.
